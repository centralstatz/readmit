## Purpose and scope

Assess two distinct, accepted proposals against the current source: [Issue #27](https://github.com/centralstatz/readmit/issues/27) removes terminal-event `available_at` and all platform eligibility behavior based on it; [Issue #26](https://github.com/centralstatz/readmit/issues/26) rejects discharge episodes later than `as_of_time` at the canonical production boundary. Both issues were read in full. This document identifies the implementation footprint, compatibility implications, and a high-level sequence; it does not implement either change or revise the existing architecture, plan, record, or release procedure.

The enduring analytical target is the probability of a first readmission strictly after `as_of_time` through the fixed endpoint 30 elapsed days after discharge. Projects still own source mapping and risk calculation; `readmit` still owns eligibility, durable history, derived CSV products, and the project-contained Shiny app. The development version stays `1.0.0.9000` until a later release-preparation step.

## Current implementation

`rrp_run()` checks analytical time, loads the configured project functions, requires initialized state, calls the project mapper through `rrp_produce_project_canonical()`, evaluates eligibility, invokes the provider for eligible rows, and writes one run and its assessments transactionally ([`R/rrp-run.R`](../../R/rrp-run.R), lines 51–91). The producer calls `rrp_check_canonical_source()` before eligibility or provider invocation ([`R/canonical-source.R`](../../R/canonical-source.R), lines 29–45). Structural checks require event identity, episode link, type, `occurred_at`, and `available_at`; both times must be finite UTC `POSIXct` ([`R/canonical-source.R`](../../R/canonical-source.R), lines 80–128). Additional canonical columns are accepted and left unchanged. The mapper is documented to supply only episodes discharged by `as_of_time`, but no comparison currently enforces that rule.

The eligibility helper derives the 30-day endpoint, marks pre-discharge episodes `not_yet_discharged`, gives closed windows precedence, and considers an event only if **both** `occurred_at` and `available_at` are at or before assessment time. It selects the earliest qualifying occurrence for each episode, with readmission winning a same-time death tie and event ID breaking remaining ties ([`R/episode-eligibility.R`](../../R/episode-eligibility.R), lines 19–63). It carries selected event identity, type, occurrence, and availability into assessment rows. The provider request contains episode identity and timing, the endpoint, and remaining seconds; it does not contain an event-availability field ([`R/provider-assessment.R`](../../R/provider-assessment.R), lines 3–15). The provider assessment passes the eligibility row through and adds probability or failure detail (lines 51–93).

`rrp_state_init()` creates `state/history.duckdb`; `assessments` includes nullable `terminal_available_at` and permits the five persisted outcomes `accepted`, `provider_failure`, `window_closed`, `known_readmission`, and `known_death` ([`R/project-history.R`](../../R/project-history.R), lines 44–62). The writer requires the availability column in assessment rows; `rrp_inspect_history()` exposes it because the reader selects `a.*` ([`R/project-history.R`](../../R/project-history.R), lines 120–145 and 183–217; [`R/project-inspection.R`](../../R/project-inspection.R), lines 77–91). Product calculation selects only run identity, analytical time, disposition, probability, discharge time, and endpoint; its three CSV schemas contain no event-availability field ([`R/analytical-products.R`](../../R/analytical-products.R), lines 8–98). The app reads those CSVs, not canonical events or DuckDB.

Project initializer copies these files; its mechanics need no change. |

The exact assessment-time rule after Issue A is: an event before or exactly at `as_of_time` can determine `known_readmission` or `known_death`; an event after that instant cannot. The closed-window precedence and existing earliest-event/tie rules remain. A previously delayed event that occurred before assessment will now affect eligibility if the mapper supplies it. No alternate timestamp, configuration mode, or historical-reconstruction mechanism is indicated.

Existing mappings that return `available_at` should remain structurally valid because [`rrp_check_canonical_table()`](../../R/canonical-source.R) permits additional columns (lines 58–69); after the change, the package must neither validate nor interpret that extra field. A mapper that already filters its own events by that timestamp still controls which rows it supplies. A mapper that supplies an earlier-occurring event with later `available_at` will see a deliberate eligibility change: the event is considered by occurrence alone. Existing user-owned project files are not overwritten by package installation or product refresh. New initialized projects receive the updated stub and guidance. This is a user-visible contract and behavior change for `NEWS.md`, not a reason for a legacy pathway.

Older `state/history.duckdb` files contain the nullable legacy column. A small isolated DuckDB/DBI diagnostic confirmed that `dbAppendTable()` can insert a data frame omitting an extra nullable table column; the omitted value becomes `NULL`. That does **not** alone prove the full upgraded-project workflow. The implementation should verify an existing 1.0.0 project can append and inspect runs under the simplified code, preserving old rows. The current `SELECT a.*` would expose `terminal_available_at` only for old databases if new schemas omit it, so an explicit inspection projection is likely needed for a stable v1.1.0 return shape. No database rewrite or migration is presently justified; existing stored values can remain physically in old project files without becoming a platform input or output.

## Issue B — Validate future discharges

The [documented source contract](../../R/canonical-source.R) says supplied episodes have discharged by assessment time (lines 14–21), but `rrp_check_canonical_source()` knows no `as_of_time` and only validates discharge timestamp type (lines 81–128). `rrp_produce_project_canonical()` already has both the validated canonical tables and `as_of_time` immediately after its structural check (lines 29–45). A short check there for any `discharge_episode$discharge_time > as_of_time` is the narrowest public-run boundary. Equality is valid. An error should name `discharge_episode$discharge_time`, `as_of_time`, and at least one offending `episode_id` (optionally their UTC values), using the existing plain `stop(..., call. = FALSE)` convention. It must occur before eligibility, provider invocation, or history writing. `rrp_project_validate()` does not invoke the mapper and should remain a structural project check.

Today the eligibility helper marks a future discharge `not_yet_discharged` ([`R/episode-eligibility.R`](../../R/episode-eligibility.R), lines 32–33), and the provider skips it. This is a coherent internal result for a direct helper call with invalid source input, but the normal public workflow should never produce it once the canonical boundary is enforced. It is not a persisted outcome. The DuckDB CHECK constraint intentionally excludes it ([`R/project-history.R`](../../R/project-history.R), lines 53–55). The current writer attempts to append the row inside a transaction (lines 162–166), causing the diagnosed CHECK failure and secondary `rapi_unregister_df` cleanup error. The [prior investigation in Issue #26](https://github.com/centralstatz/readmit/issues/26) found rollback leaves no partial history and preserves earlier runs; this assessment independently verified the same code path, not a new runtime reproduction. Early validation removes this particular database failure path without changing the CHECK constraint, eligibility status model, or general DuckDB error handling.

Focused regression coverage belongs at the production boundary and through `rrp_run()`: reject a future discharge with an informative error; accept discharge exactly at `as_of_time`; prove an invalid canonical result prevents calls to a provider that would otherwise be eligible; verify zero new runs/assessments on a rejected first run and unchanged earlier history after a rejected later run; and verify a historical run succeeds when the mapper supplies only already-discharged episodes. [`test-rrp-run.R`](../../tests/testthat/test-rrp-run.R), lines 206–225, already tests rollback for a future discharge but currently accepts any opaque error; that expectation should become a clear upstream error and no-provider assertion. [`test-canonical-source.R`](../../tests/testthat/test-canonical-source.R) covers structural failures and is the natural place for the temporal boundary and equality checks. [`test-episode-eligibility.R`](../../tests/testthat/test-episode-eligibility.R), lines 32–50, currently documents the internal pre-discharge marker and need not force a persisted status. The getting-started vignette's static mapper is valid for its chosen January 10 snapshot; a concise as-of discharge filter with matching event selection would make its source-population responsibility clearer for readers experimenting with earlier dates, but is not required to fix the runtime defect.

## Cross-issue dependencies and boundaries

Both issues touch [`R/canonical-source.R`](../../R/canonical-source.R), `test-canonical-source.R`, and `test-rrp-run.R`; Issue A also changes eligibility, history shape, the reference article, and broader documentation. Issue B's `discharge_time` comparison is independent of event availability. Implementing B first makes the existing defect testable under the current contract; implementing A afterward requires adapting the B fixture to four-field events. Each can be verified separately, then together through an installed-project assessment, history inspection, product refresh, and the existing Shiny smoke path. No change is required to the public function names, provider-request fields, the 30-day endpoint, product schemas, project-owned app code, or project initialization mechanics.

The original January 7, 11:59 reproduction cannot retain its old expected dispositions after Issue A. With its supplied events and only `occurred_at` used, episode 2's January 6 readmission is already known; episode 3 is window-closed; episode 4's January 7, 12:00 death is still future. Episode 1 remains invalid until filtered out or rejected. At January 7, 12:00, episode 4's death is also known. Tests must separate the future-discharge error from these deliberately changed event outcomes.

## Risks and open questions

The material compatibility risk is an existing user-owned DuckDB history with a legacy nullable column: subset insertion worked in a small diagnostic, but the full upgraded-project run/read path needs regression verification. The inspector's `a.*` must not yield different public columns according to database age. A second practical risk is that the simulated walkthrough's event-availability removal changes seeded data generation and observed outcomes; its explanatory claims and executable assertions must be rechecked. Existing mappings that use `available_at` for their **own** filtering remain the owner's choice; mappings that supply later-available events without filtering will see the intentional new eligibility behavior. These are implementation and communication checks, not unresolved architectural choices. The two issues and existing contract provide sufficient direction; no maintainer decision is required before focused implementation planning.

## Recommended next steps and conclusion

After maintainer review, plan the two workstreams separately: first enforce the future-discharge contract and verify the focused failure/equality cases; then remove event availability from the package, fixtures, synthetic article, and documentation; finally verify the integrated installed-project workflow, old-history read/write behavior, products, Shiny smoke behavior, and package checks. Keep `DESCRIPTION` at `1.0.0.9000` throughout implementation and defer the exact `1.1.0` version transition to release preparation under [`dev/release-procedure.md`](../release-procedure.md).

Both changes are feasible within a focused v1.1.0 release. Issue A is broader than a one-condition eligibility edit because availability also shapes history, tests, and the executable reference article; it does not require a new analytical architecture. Issue B remains a small contract-enforcement fix. No unexpected product or Shiny dependency, source-history corruption, or need for new infrastructure was identified.
