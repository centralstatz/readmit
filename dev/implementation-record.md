# readmit v1.0.0 — Implementation Record

## Purpose and maintenance

This document records what the `readmit` repository currently implements. `dev/architecture.md` describes the intended product, and `dev/implementation-plan.md` describes the planned sequence. Record completed behavior and its evidence here, organized by the plan's stage and increment identifiers. Do not treat planned operations as implemented.

Each increment section describes its **current** implementation. When later work changes an earlier component, update the affected section rather than appending a duplicate entry or a chronological log; Git retains earlier versions. Use the simple statuses `In progress`, `Implemented`, `Verified`, and `Needs revision` according to the available evidence. Record dates only when supported by Git history or a performed check. Keep verification proportional to the functionality, without a separate evidence or qualification system.

## Current implementation status

- **Overall stage:** Stages 1 — Complete Structural Scaffolding, 2 — Project Authoring and Canonical Source, 3 — Risk Assessment and Persistent History, 4 — Analytical Products, and 5 — Populated Shiny App are **Verified / Complete**.
- **Available now:** A conventional, installable R package; `rrp_project_init()` creates user-owned resources and a Shiny app, `rrp_project_validate()` checks structural authoring setup, and `rrp_state_init()` creates project-owned DuckDB history. After the owner implements both authoring scripts, `rrp_run(path, as_of_time)` retains completed assessments. Public `rrp_project_status()` and `rrp_inspect_history()` read retained outcomes, and `rrp_refresh_products(path)` produces three analytical CSVs from that history without another assessment. The project app reads those CSVs and offers an interactive Current Risk Pool with selected-episode history and a snapshot-level Overview.
- **Not yet complete:** Stage 6 — v1.0.0 Product and Release Readiness. Increments 6.1–6.5 are **Complete**; 6.6 is **In progress** with 6.6.A Complete and 6.6.B Planned / Not started, and 6.7–6.8 remain. A package app launcher is not planned.
- **Current use and limitation:** Create a project, implement its source mapper and provider, validate its structure, initialize state, run assessments at UTC analytical times, inspect retained results, and explicitly refresh product CSVs. Completed runs append history without revising earlier assessments; refresh reads history without running the mapper or provider. The project app launches before products exist; after refresh it displays current and historical risk plus unfiltered operational and accepted-current-risk summaries. Application runtime packages are in `Suggests` for tests, not core `Imports`.
- **Next step:** A separate maintainer instruction to begin planned 6.6.B website implementation. No website redesign or release execution has begun.

##### 6.2.B — Release Procedure Design

- **Status:** Complete.

**Approved lifecycle and stage boundary.** Stage 6.7 finishes implementation and public documentation, prepares the development NEWS entry and CRAN comments, reviews the earlier CRAN package and license transition, checks existing CRAN results and applicable reverse dependencies, performs local and external checks, and ends with a reviewed development-version release candidate. It does not submit or publish. Stage 6.8 then performs the version transition, checks the exact release-version source, submits and handles CRAN correspondence, publishes only after acceptance, and returns to development. Checks on the 6.7 development version do not replace checks after the release version or any correction changes the source.

**Version, submission, and corrections.** For the initial submission, `usethis::use_version("major")` changes `0.0.1.9000` to `1.0.0` and turns the leading development NEWS heading into a release heading; in an interactive Git project it can offer a commit and optional push. Check the resulting files and Git state, ensure the intended release source has a clean commit, then build and run appropriate CRAN-style checks on that release-version source. `devtools::submit_cran()` builds and uploads a source package; after upload it writes a temporary `CRAN-SUBMISSION` record with version, time, and current Git SHA. The maintainer must confirm CRAN's email; upload and confirmation are not acceptance. For a rejection or requested correction, change only the necessary source, normally use `usethis::use_version("patch")` unless CRAN directs otherwise, review the new NEWS heading and notes so unreleased notes are assigned correctly, add a concise resubmission account to `cran-comments.md`, commit the corrected source, rerun relevant exact-version checks, and submit again. A new successful upload updates the submission record for that version and commit. No rejected version is published on GitHub as an accepted release.

**Provenance and publication.** The accepted version, submitted package source, clean release commit, and latest `CRAN-SUBMISSION` record must agree before GitHub publication. `submit_cran()` builds a fresh bundle, so separately built archives are not claimed byte-identical; GitHub's automatic source archives are repository snapshots rather than CRAN-built package bundles. After CRAN confirms acceptance, verify the record's version and SHA, then use `usethis::use_github_release()`. It can push the branch and creates the `v<accepted version>` GitHub tag/release at the recorded commit, then removes the temporary record after success. Do not rely on its current-HEAD fallback when the submission record is missing without checking the accepted source identity. Only after GitHub publication, run `usethis::use_dev_version()` from the accepted release version; it updates `DESCRIPTION` and adds the new development NEWS heading, and may offer a Git commit and optional push. Thus acceptance of `1.0.0` leads to `v1.0.0` and `1.0.0.9000`, while a corrected accepted `1.0.1` leads to `v1.0.1` and `1.0.1.9000`.

**Communication and 6.2.C handoff.** The eventual CRAN comments will identify `readmit` as an update to the existing `0.0.1` package, state the intentional RRP purpose and breaking API change, highlight MIT to Apache License 2.0, and report actual checks and any resubmission response; update them for the exact release-source results in 6.8. `NEWS.md` will describe the RRP release under the development heading until version transition and retain the `0.0.1` history; Stage 6.3 owns README and related public messaging.
