# readmit v1.0.0 — Implementation Record

## Purpose and maintenance

This document records what the `readmit` repository currently implements. `dev/architecture.md` describes the intended product, and `dev/implementation-plan.md` describes the planned sequence. Record completed behavior and its evidence here, organized by the plan's stage and increment identifiers. Do not treat planned operations as implemented.

Each increment section describes its **current** implementation. When later work changes an earlier component, update the affected section rather than appending a duplicate entry or a chronological log; Git retains earlier versions. Use the simple statuses `In progress`, `Implemented`, `Verified`, and `Needs revision` according to the available evidence. Record dates only when supported by Git history or a performed check. Keep verification proportional to the functionality, without a separate evidence or qualification system.

## Current implementation status

- **Overall stage:** Stages 1 — Complete Structural Scaffolding, 2 — Project Authoring and Canonical Source, and 3 — Risk Assessment and Persistent History are **Verified / Complete**. Stage 4 — Analytical Products is **In progress**; 4.1 is its latest verified increment.
- **Available now:** A conventional, installable R package; `rrp_project_init()` creates user-owned resources and an empty-state Shiny app, `rrp_project_validate()` checks structural authoring setup, and `rrp_state_init()` creates project-owned DuckDB history. After the owner implements both authoring scripts, `rrp_run(path, as_of_time)` retains a completed assessment and returns its run ID and outcome counts. Public `rrp_project_status()` and `rrp_inspect_history()` read project identity and retained outcomes without sourcing analytical scripts. A complete installed-package Stage 3 workflow has been verified across fresh R processes. Internal Stage 4.1 calculations now derive three in-memory product data frames from retained history.
- **Not yet available:** Public product refresh, product CSVs, or populated Shiny views. A package app launcher is not planned.
- **Current use and limitation:** Create a project, implement its source mapper and provider, validate its structure, initialize state explicitly, run assessments at UTC analytical times, and inspect project status and stored assessment rows. Status works before state; history inspection requires state. Completed runs append history without revising earlier assessments. The internal product calculation is not yet a user-facing refresh operation; the project app remains empty, and application-only packages are not package dependencies.
- **Next step:** Implement Stage 4.2 — Product Refresh and CSV Writing.

**Product meaning.** `current_risk` has one row per `accepted` or `provider_failure` assessment in the selected run, ordered by episode ID. Repeated-time runs remain separate observations; currently ineligible or absent episodes contribute none. `scope` contains exactly one row of selected-run counts, including zero-episode runs. Its eligible count is accepted plus provider failures, its ineligible count is the sum of closed-window, known-readmission, and known-death outcomes, and its eligible count matches the current-risk row count. No eligibility is recalculated from current source data.
