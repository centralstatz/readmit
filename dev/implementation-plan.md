# readmit v1.0.0 — High-Level Implementation Plan

## Purpose and approach

This plan describes the current route from the minimal `readmit` R package to a minimally working v1.0.0 release. `dev/architecture.md` describes the current intended product; this plan describes the current intended sequence for building it. Neither document is frozen. Implementation findings may justify simplifying or revising either one, and Git will preserve those changes. Detailed planning occurs one stage at a time, immediately before that stage begins.

Build a complete structural skeleton first, then make its ordinary project workflow work from end to end. Keep the package valid and installable throughout. Use familiar R package tools, direct functions, focused tests, and `R CMD check` after implementation increments. Later stages may be divided, combined, or reordered as the working code clarifies what is needed. Stop when the agreed minimal v1.0.0 functionality works; no separate qualification or change-control system is needed.

### Stage 2 — Project authoring and canonical source

- **Objective:** Make the two ordinary project authoring points usable.
- **Major scope:** Load project configuration and the supplied source and provider functions; make project validation useful; document the minimal discharge-episode and terminal-event input contract, including the expectation that supplied episodes have been discharged by analytical time `t`. Add only checks needed for operations to proceed.
- **Expected outcome:** A project owner can supply canonical data through the source-mapping script according to a clear contract; the package can use those shared facts for later eligibility and history.
- **Verification:** Focused tests with small test-suite fixtures for project loading, essential structure, and use of the documented canonical input; package check.
- **Dependencies or boundaries:** Requires Stage 1 project files and resources. Defer assessment persistence and products. The project author owns source population, clinical definitions, source quality, and private model predictors; source-data auditing and clinical validation are outside this stage.

**Starting point and authoring boundary.** Stage 1 already creates `rrp-project.dcf` with `Project-ID`, `rrp-authoring.dcf` with `Source-Mapping-Script` and `Risk-Provider-Script`, and the two scripts under `R/`. Keep `rrp_produce_canonical(project_root, as_of_time)` and `rrp_calculate_risk(project_root, request)` as the only required project-authored functions. The package finds and loads them; there is no registration file. Stage 2 may invoke the producer in a focused workflow to establish its canonical return, but does not construct provider requests or invoke the provider for assessments. Project scripts are trusted R code, and sourcing them can execute top-level expressions; loading is not a security sandbox.

**Configuration and loading choice.** Use base `read.dcf()` to read one record from each existing DCF file. Require the three current fields to be present and nonempty, and resolve the configured project-relative script paths against the explicit project root. A small internal helper can source each script into a fresh environment and obtain the named function with the documented arguments; report missing files, unreadable DCF, sourcing errors, or missing/non-function bindings with plain errors. Do not add DCF fields, an object hierarchy, registration, dependency installation, or a general path-management system. Function loading is distinct from calling the source mapper, checking its returned data, and running later risk assessments.

**Working canonical input contract.** Document this contract with the Stage 2 package and project authoring guidance when it is implemented. It follows the architecture's two domains and uses the historical platform's descriptive names without its bundle envelope or contract machinery. The producer returns a named list of two ordinary data frames; both may have zero rows, with their required columns still present.

| Table | Required columns and meaning |
| --- | --- |
| `discharge_episode` | `episode_id`: stable episode identity; `patient_id` and `index_encounter_id`: patient and index-encounter context; `admission_time` and `discharge_time`: encounter times. |
| `terminal_event` | `terminal_event_id`: event identity; `episode_id`: related discharge episode; `event_type`: `readmission` or `death`; `occurred_at`: event time; `available_at`: when the event became known to the analytical system. |

Use nonempty character identifiers and `POSIXct` instants in UTC for `as_of_time` and the timestamp columns; use ordinary character values for `event_type`. The author supplies episodes discharged by `as_of_time` and owns source population, clinical definitions, mapping, and data quality. The author also supplies truthful occurrence and availability times. `followup_window_end` is not an input field: Stage 3 derives the fixed endpoint as `discharge_time + 30 * 24 * 60 * 60` seconds when assessing episodes. An event can have occurred by `t` while becoming available later; it is not known at `t`. Stage 3 must use **both** `occurred_at <= t` and `available_at <= t` when interpreting known terminal events. Do not assume all returned events were known at `t`, and do not treat a future-available event as current evidence. Source-native IDs, crosswalks, and private model predictors stay in project-controlled code and data.

The consuming helper should check canonical structural integrity: the two named data frames, required columns and usable basic types, nonmissing identities and required timestamps, unique episode and terminal-event IDs, recognized event types, and terminal-event episode IDs that resolve to supplied episodes. Give a clear error for unusable input. There is no supplied endpoint to check. Do not add timestamp-ordering rules solely for later eligibility, readmission/death sequencing, or the assessment cutoff; those interpretations belong to Stage 3. Document the producer's discharge-by-`t` population responsibility without claiming to verify the clinical source population or mapping. Exact user-facing wording and small implementation details can be settled while documenting the contract; do not create a parallel schema authority or broad source-data validation framework.

**Historical reference.** The previous platform's two domain names, project-supplied fact fields, function names, and occurrence-versus-availability distinction are useful analytical references. Its supplied follow-up endpoint is not carried forward because that value is platform-derived here. Its use of DCF and `sys.source()` also illustrates direct R loading. Its RFC 3339 parser, versioned envelopes, catalogs, registration layer, strict admission machinery, and broad validation are not needed for this simpler R data-frame interface. The `POSIXct` choice follows familiar R practice; any implementation code reused from the historical repository should be limited to direct behavior that fits this contract.

**Ordered implementation increments.** Each increment should leave the package installable and use focused `testthat` tests and `R CMD check` for the behavior it adds.

1. **Project configuration and authoring-function loading.** Add a small internal loader in `R/` for the two DCF records and their configured project-relative scripts. It checks essential fields, sources each authoring file without polluting the global environment, and returns the two expected callable bindings. **Deliverable:** project functions can be located and loaded from a Stage 1 project without running either function. **Verify:** small temporary-project tests for the normal template, a changed configured script path, and clear missing/malformed file or binding errors. **Boundary:** no producer or provider invocation, canonical validation, public validation function, state, or app dependency.
2. **Canonical contract and source-mapper use.** Document the two data frames, columns, types, `as_of_time`, discharge-population expectation, occurrence/availability distinction, and package-owned 30-day endpoint in the relevant roxygen help and generated project guidance; keep the two existing authoring signatures. Add a direct internal call to `rrp_produce_canonical(project_root, as_of_time)` and the structural return checks above, separate from the loader. **Deliverable:** a project-supplied producer can return usable canonical facts through the package, including an empty event table, without an analytical run. **Verify:** a small test-suite fixture with multiple episodes, readmission/death event types, and a delayed-availability event, with no endpoint column; test missing required columns, unusable types, duplicate identities, invalid event types or episode references, and missing required timestamps. **Boundary:** no endpoint calculation, eligibility decisions, history writes, provider calls, or model-predictor checks.

Return `invisible(TRUE)` on success; stop with a specific, plain error on the first essential failure. **Deliverable:** an analyst can check a project's structural readiness before attempting analytical work. **Verify:** the generic initialized project passes despite its deliberate function-body stubs; missing files, invalid DCF, and absent functions fail clearly. **Boundary:** sourcing scripts to obtain bindings is allowed, but validation does not call either authoring function, inspect live source data, initialize state, or certify a model. The app, branding, and README are not analytical readiness gates.

### Stage 3 — Risk assessment and persistent history

- **Objective:** Execute the fixed remaining-readmission-risk target and retain assessments across runs.
- **Expected outcome:** A user-owned project can run assessments at multiple explicit UTC times and inspect accepted estimates, provider failures, and ineligible episodes after later runs and fresh database connections.
- **Starting point and boundary:** Stage 2 supplies project loading, structural validation, and canonical source production, but no assessment or state operation. The project owns the discharge population, clinical definitions, private predictors, and risk methodology; `readmit` owns eligibility, the fixed estimand, provider request and result acceptance, and history. Stage 4 products and Stage 5 app data display remain separate. Use direct R functions, ordinary lists and data frames, and a small DuckDB history rather than a model or persistence framework.

**Analytical contract.** The target is the probability of a patient's first readmission in the remaining follow-up period, conditional on information available at assessment. Validate `as_of_time` as one finite UTC `POSIXct` instant, as Stage 2 does. For each supplied episode, derive `followup_window_end = discharge_time + 30 * 24 * 60 * 60` seconds. The episode is eligible at or after discharge and while `as_of_time < followup_window_end`; the requested risk covers times strictly after `as_of_time` through the inclusive endpoint. Among events for that episode, only those with both `occurred_at <= as_of_time` and `available_at <= as_of_time` are known. Use the earliest known terminal event by occurrence time; a readmission wins an equal-time readmission/death tie. A known first readmission or prior death makes the episode ineligible. Delayed-availability events remain in canonical facts and may affect a later assessment. Recommend simple ineligible dispositions `window_closed`, `known_readmission`, and `known_death`, with the closed window taking precedence at or after its endpoint. A pre-discharge episode is testable in the eligibility helper as ineligible, but the Stage 2 mapper contract already requires discharges by analytical time; do not add a special persisted outcome or source-population audit for such input. Keep provider failure distinct from ineligibility.

**Provider contract.** Invoke `rrp_calculate_risk(project_root, request)` once per eligible episode; there is no batch mode. Use a named list request containing `episode_id`, `patient_id`, `index_encounter_id`, `admission_time`, `discharge_time`, `as_of_time`, `followup_window_end`, and derived `remaining_seconds`. The last three fields state the fixed estimand and remaining horizon; `project_root` lets the project obtain private predictors without passing them through canonical tables. The requested episode supplies the result association, so no returned identifier or batch matching is needed. The approved return forms are exactly `list(probability = <one finite numeric in [0,1]>)` or `list(failure = <one nonblank character reason>)`. An explicit failure, unusable result, or error thrown while invoking one episode's provider becomes that episode's `provider_failure`, with `failure_kind` distinguishing `reported`, `unusable_result`, and `error`; continue other episodes. A failure in canonical production or persistence is run-fatal. Do not inspect private predictors, prescribe the model, or add retries or provider infrastructure.

**State and history.** Keep state separate from user-authored files at `state/history.duckdb`. `rrp_state_init(path)` explicitly creates `state/` and a small DuckDB database after checking the project; `rrp_run()` requires initialized state and never creates it implicitly. A separate `state.dcf` is unnecessary unless implementation reveals metadata that the existing project DCF and database cannot hold. Use two ordinary tables, one row per completed run and one row per episode supplied through the normal documented workflow in that run:

| Table | Minimum durable fields | Why they are retained |
| --- | --- | --- |
| `runs` | `run_id`, `project_id`, `as_of_time`, `created_at`, `source_mapping_script`, `risk_provider_script` | Identify each actual execution and its analytical time; the configured script references give modest source/provider context without a provenance system. |
| `assessments` | `run_id`, `episode_id`, `patient_id`, `index_encounter_id`, `admission_time`, `discharge_time`, `followup_window_end`, `disposition`, nullable `probability`, nullable `failure_kind`, nullable `failure_reason` | Link repeated assessments to one episode, preserve the assessed interval and result, distinguish accepted risk, provider failure, and ineligibility, and support later trajectories and scope counts. |
| Selected event columns on `assessments` | Nullable `terminal_event_id`, `terminal_event_type`, `terminal_occurred_at`, `terminal_available_at` | Populate only when the earliest known event determines `known_readmission` or `known_death`. The ID identifies the selected event among multiple or tied events; type and both times explain the disposition and when it became knowable. Do not copy other terminal events. |

Use dispositions `accepted`, `provider_failure`, `window_closed`, `known_readmission`, and `known_death`; accepted probability is present only for `accepted`, and failure detail only for `provider_failure`. The selected event columns are empty for other dispositions. A delayed event does not change an earlier assessment; a later run may record it if it is then known. Keep private predictors and full canonical tables out of history. The historical platform's actual risk trajectories used episode identity, run/assessment time, and accepted probability, while scope summaries counted outcomes; its much larger version, contract, and revision metadata is not needed here.

Assign a distinct run ID to every completed run, including repeats at the same `as_of_time`; never overwrite earlier assessments. Store and read UTC instants consistently, verifying their round trip. Open and close a DuckDB connection per state operation. Compute outcomes before a short transaction that inserts the run and all its assessments atomically; rollback on a fatal source, database, or other run-level error, leaving no partial completed run. Episode-level provider failures remain valid rows in a completed run. History is authoritative; Stage 4 will derive CSV products separately.

`rrp_run(path, as_of_time)` returns a small ordinary R summary containing `run_id`, `as_of_time`, `episodes_processed`, `accepted`, `provider_failures`, and `ineligible`; a brief completion message is optional. `rrp_project_status(path)` reads configuration without sourcing project scripts and returns project ID, whether state exists, run count, and latest run identity/time; before state it reports zero runs. Latest means most recently recorded by execution time, not greatest analytical `as_of_time`; ties use a deterministic run-ID order. Stage 4 can add product availability without changing these fields. `rrp_inspect_history(path, run_id = NULL, episode_id = NULL)` requires initialized state and returns stable, typed, read-only assessment rows with run context and optional exact filters; empty history or unmatched filters yield the same typed zero-row structure. Zero-episode runs count in status but add no assessment row. Neither inspection operation sources or invokes project-authored functions. No products or additional convenience API are part of Stage 3.5.

**Ordered implementation increments.** Each increment should have focused `testthat` coverage and leave the package installable. Use small deterministic project fixtures, not a synthetic EHR generator.

1. **3.1 — Analytical time and eligibility.** Implement a direct internal operation over Stage 2 canonical data that derives the endpoint, one disposition per supplied episode, and the selected known terminal event when one determines ineligibility. **Deliverable:** deterministic eligible/ineligible results without a provider or database. **Verify:** pre-discharge handling, within-window time, exact/beyond-endpoint time, known readmission and death, simultaneous events, delayed availability, multiple events for one episode, and multiple episodes for one patient. **Dependency/boundary:** reuse Stage 2 structural checks; do not add broad clinical input policing or persist pre-discharge exceptions.
2. **3.2 — Provider request and result handling.** Implement one invocation per eligible episode and a small result interpreter; preserve the generated provider's two-argument signature while documenting its request and exact result encoding. **Deliverable:** accepted probabilities or isolated provider-failure outcomes ready for a run. **Verify:** request identity and remaining-horizon fields, probability boundaries 0 and 1, reported failure, unusable result, and thrown error; other episodes continue and ineligible episodes never reach the provider. **Dependency/boundary:** requires 3.1; no batch mode, training, predictor validation, plugin system, or persistence yet.
3. **3.3 — Project state and history storage.** Add `rrp_state_init(path)` and small internal DuckDB connection/write/read helpers, declaring only the dependencies actually used (normally `DBI` and `duckdb`). **Deliverable:** explicit, durable two-table history with the selected event context above and no analytical run. **Verify:** fresh initialization, refusal to overwrite existing state, an empty history read, UTC and nullable-field round trips, closed connections, distinct repeat-run IDs, intact earlier rows, and rollback of a failed atomic write. **Dependency/boundary:** requires a valid Stage 1–2 project; no migration, alternate backend, products, or backup lifecycle.
4. **3.4 — Integrated assessment run.** Export `rrp_run(path, as_of_time)` using Stage 2 canonical production, 3.1 eligibility, 3.2 per-episode provider handling, and 3.3 persistence. **Deliverable:** a concise completed-run summary and one durable accepted, provider-failed, or ineligible assessment per episode supplied through the normal documented workflow. **Verify:** only eligible episodes reach the provider; reported, unusable, and thrown provider failures are recorded without stopping other episodes; source or fatal write errors leave no partial run; zero-episode runs are inspectable. **Dependency/boundary:** requires 3.1–3.3 and explicit state initialization; no product refresh or app changes.
5. **3.5 — Status and history inspection.** Export `rrp_project_status(path)` and `rrp_inspect_history(path, run_id = NULL, episode_id = NULL)` with concise documentation. **Deliverable:** compact project/run status, including the most recently recorded run even when its analytical time is earlier, and stable typed assessment rows. **Verify:** status before state and before runs, history requiring state, typed empty and unmatched reads, exact run/episode filtering, zero-episode runs counted without fabricated rows, retained outcome and selected event context, and no project-script sourcing or invocation during reads. **Dependency/boundary:** requires 3.3–3.4; no CSV products or extra convenience API.
6. **3.6 — Installed-package workflow and check.** In a temporary project, implement small source and provider functions, initialize state, run at different and repeated analytical times, then inspect earlier outcomes through fresh package sessions or database connections. **Deliverable:** verified durable Stage 3 analytical workflow, updated concise package/project guidance, and an accurate implementation record. **Verify:** availability-sensitive eligibility, distinct append-only repeat runs, unchanged earlier event knowledge, retained accepted and provider-failed outcomes, selected event context, UTC round trips, provider non-invocation for ineligible episodes, full tests, installation, build, and `R CMD check --no-manual`. **Boundary:** no Stage 4 products or Stage 5 populated views.

**Stage boundaries.** The maintainer has settled provider granularity, return encoding, failure isolation, minimal history, repeat-run behavior, atomic persistence, and simple public outputs. Stage 4 history selection and product schemas were deferred to Stage 4 planning. Implement each Stage 3 increment within its stated scope.

### Stage 4 — Analytical products

- **Objective:** Turn retained history into the three established analytical product categories.
- **Major scope:** Generate current remaining risk, observed risk trajectories, and operational scope summaries; implement the separate product-refresh operation and write project-owned CSV data under the state area.
- **Expected outcome:** A completed run can produce readable files for analysis and app consumption without executing another assessment. Its scope summary describes the assessed population and retained outcomes.
- **Verification:** Focused checks of product meaning against retained history, including an empty or zero-result case where meaningful; package check.
- **Dependencies or boundaries:** Requires Stage 3 history. Source-history selection and CSV details are specified below. Do not add an elaborate freshness framework or modify app source during refresh.

**Starting point and history boundary.** Each `rrp_run()` is a snapshot of the discharge episodes supplied by the project source mapper at analytical `as_of_time`, including a valid snapshot of zero episodes. Stage 3 retains one `runs` row per completed snapshot and one `assessments` row per supplied episode. `run_id` distinguishes repeats at the same `as_of_time`; `created_at` records execution time, which may have a different ordering. Stable `episode_id` connects assessments across runs. Assessment rows retain accepted probabilities or provider-failure and ineligible dispositions, with terminal-event context where applicable. Read-only run and assessment helpers can supply products without invoking project scripts. `rrp_inspect_history()` exposes joined assessment rows but omits zero-episode runs, so product calculations must read the run table too. `rrp_project_status()` calls the most recently *recorded* run latest; that existing field has a different meaning from the current product snapshot. The intended operational workflow periodically reassesses the complete relevant discharge population. The project owner supplies a coherent, complete relevant cohort; `readmit` applies its clinical eligibility rules to that supplied cohort. The owner need not reproduce those rules in source queries.

**Analytical product meanings.** Clinical eligibility determines current risk-pool membership; prediction success determines whether a member has an accepted estimate. The current remaining-risk product contains one row for every clinically eligible episode in the selected run: `accepted` with its probability, or `provider_failure` with a missing probability. Both outcomes passed Stage 3 eligibility. `window_closed`, `known_readmission`, and `known_death` are clinically ineligible and excluded. A provider failure, including repeated failures, does not remove an episode or imply zero risk. Never substitute an earlier accepted probability for a failed current assessment. Eligibility retains Stage 3's 30-day and event occurrence/availability rules.

Observed trajectories contain actual accepted assessments at discrete analytical times for episode IDs in that *current clinically eligible pool*, including distinct repeated-time runs. A currently eligible episode with a failed estimate may have earlier accepted trajectory observations, but no accepted observation at its failed assessment time; an episode with no accepted history has no trajectory rows. Currently ineligible or absent episodes have no trajectory rows. Retain each observation's run identity and order by analytical time, then execution time and run ID. Do not interpolate, smooth, carry forward values, or infer intervention effects. The operational scope is one row of mutually exclusive outcome counts for *all* assessments in the selected run, including eligible and ineligible episodes; it does not count unique patients or all historical assessment rows. `eligible_count = accepted_count + provider_failure_count`, `ineligible_count = window_closed_count + known_readmission_count + known_death_count`, and `episodes_assessed = eligible_count + ineligible_count`. The current-risk CSV must have exactly `eligible_count` rows. These counts distinguish clinical eligibility, prediction outcome, and estimate availability; no additional rate calculations are required.

**Current snapshot selection.** Select the completed run with the greatest `(as_of_time, created_at, run_id)`, compared in that order. This gives current risk and scope one analytical time and one supplied population, with a deterministic choice among repeats. A subsequently executed historical backfill cannot replace a snapshot at a later analytical time. For trajectories, use accepted rows at or before the selected analytical time for IDs in the selected *eligible* pool. Keep each repeated-time observation and its `run_id`; a later-executed older-time run may add a historical observation without replacing current risk. “Current” means the selected analytical snapshot, not necessarily live clinical status. A partial later run is permitted but, if selected, replaces the larger earlier snapshot: for example, a later run of 100 failed episodes replaces an earlier run of 10,000 episodes in current products. Earlier episodes are not merged into it. Operational product refresh should therefore follow a complete-population assessment. Do not add completeness enforcement, retry reconciliation, automatic merging, or a public run selector.

**CSV products.** Write three UTF-8 files under `state/products/`. All include headers; identifiers and dispositions are character, available `probability` values are numeric in `[0,1]`, missing probabilities use an empty CSV field rather than zero, counts are nonnegative integers, and UTC timestamps use unambiguous ISO 8601 text with fractional seconds and `Z`. The scope row identifies the selected run even when either episode file has no rows. Keep the fixed schemas simple, without another contract authority.

**Refresh behavior.** `rrp_refresh_products(path)` reads retained history, calculates the three products, and replaces the project-owned CSVs without another assessment. Require initialized state. Missing state or state with no completed runs produces a clear error without creating or replacing products; no runs must not be presented as a completed zero-episode run. A completed zero-episode run writes two header-only episode files and a zero-count scope row. An all-ineligible run also has two header-only episode files. An all-provider-failure run writes one current-risk row per eligible episode with a missing probability; its trajectory may contain earlier accepted observations for those same episodes. When accepted and failed eligible episodes occur together, both appear in the current-risk file. An eligible episode with no accepted history remains in current risk even though it has no trajectory row.

Read a consistent view of required history, calculate all three data frames, check their fixed structures and basic disposition/count invariants, then write and check all three temporary CSVs before replacing existing outputs. A calculation, validation, or staging failure leaves prior products unchanged. Staging does not make the final three-file replacement fully atomic; a failure during replacement may leave a partly updated set. Do not add manifests, transactional publication, backup/recovery workflows, or generalized file management. Repeated refresh against unchanged history yields equivalent analytical content; new history appears after the owner refreshes again. History remains authoritative. Refresh does not source or invoke project functions, change retained assessments, edit project-authored scripts or app files, require app execution, or enforce freshness. Stage 5 will read the files into the existing app regions and handle absent or empty products.
